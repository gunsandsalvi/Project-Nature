# AR1: review of P1 (A1–A3) and P9 (A14–A17)

### 1. [blocker] A15.4, A15.8, A17.8, A17.10 GitHub releases can't be made from a session
Problem: Century checkpoints go to a release `run-<id>` (A15.8's Decision, A17.8), test worlds over 50 MB to `stage-<n>-worlds` (A15.4), and APKs to release assets past 2 GB (A17.10). No session can upload a release: `gh` is installed but its `GH_TOKEN` is invalid (`gh auth status` fails), the GitHub MCP only lists and reads releases, and git push reaches only the session's branch and refuses files over 100 MB. So B80's open question (where checkpoints live between sessions) is still open, and `PLT-05`'s large test worlds have no way to the phone. A15.8 also sizes the full pace test at 20 worlds; `RES-07` says 10 worlds to Year 500, 20 to Year 60 nightly and 20 to Year 150 at `MIL-06`'s close.
Fix: runs never leave the machine. Each run is sized to finish inside its session: files survive container restarts (B80), the 30-minute `send_later` wake restarts dead runs from local checkpoints, and a lost session reruns its worlds the next night. Costs at A16.3's budget, cloud = phone-held ÷ 1.5: nightly 20 worlds × 3,600 game days at ~130 people ≈ 7 CPU-hours (one session, ~2 h); `MIL-06` 20 × 9,000 days at ~180 people ≈ 20 CPU-hours (two sessions, ~3 h); full test 10 × 30,000 days at 1,000–1,300 people on average (`BIO-04`'s 0.8% growth from ~100) ≈ 100–130 CPU-hours: each world on 2 workers, 2 worlds per session, 5 sessions, ~7–9 h. Commit only `runs/<id>/status.json` and results. Owner-facing test worlds: exports split into ≤ 45 MB parts (`.kindling.001`, …) that import joins from a multi-file pick, committed in `dist/worlds/`. Delete A17.10's release fallback. Optional, with the owner's OK: a fine-grained token for this repository only (Contents and Commit statuses, read and write) as the environment variable `KINDLING_GH_TOKEN`, used as `GH_TOKEN=$KINDLING_GH_TOKEN gh release …` after a 1 MB test upload through the proxy in the first alpha; it also serves findings 2 and 4.
Part: P9

### 2. [blocker] A15.12, A15.13 The merge gate can't be set up or fed
Problem: `main` is to require the statuses `kindling/checks` and `kindling/review`, set up "once with the owner's account" by an agent, with builder and reviewer setting the statuses. No session tool can set a commit status or branch protection (no working `gh`; the GitHub MCP has neither call), so either nothing can merge or nothing is enforced, and `PRC-09`'s Check fails. Step 5 has `tools/check.sh`, a shell script, compare the reviewer's session from a PR comment it cannot read. `PRC-09`'s second fresh reviewer, after one disputed round of fixes, is missing.
Fix: the owner, once, in GitHub's settings on the phone: protect `main` (pull request required, force pushes blocked). The merging agent calls `merge_pull_request` only when (1) `results/checks/<head sha>.json`, written by `tools/check.sh`, is on the branch with every step passed, and (2) a PR comment `Review: APPROVE <head sha> <reviewer session>` names a session absent from the branch's `Claude-Session` trailers; any later push voids the approval; the agent records both in `results/reviews/<pr>.json`. `tools/idcov.py --stage` re-checks every merge commit on `main` and lists gaps in the stage report. Add the second-reviewer rule. With the owner's OK (`SCP-15`), a ~30-line `.github/workflows/gate.yml` on the free public-repository runners reads the same evidence and sets both statuses with `GITHUB_TOKEN` (`statuses: write`), so protection can require them; it runs for seconds and never runs the checks themselves.
Part: P9

### 3. [major] A14.6, A14.7, A16.5 Autosave every 120 s breaks `PLT-07`'s 30 s
Problem: `PLT-07` (Decided) saves the present state "at least every 30 real seconds"; A14.6 saves every 120 s (300 s overnight, copied by A4.11) and A14.7/A16.5 accept catch-ups of up to 120 s or 300 s. At the end of the arc A14.4 keeps the world paused while the workers compress up to 200 MB (≤ 0.6 s); every 30 s that is 2% of the world's time.
Fix: every 30 real seconds, in play and overnight; catch-up ≤ 30 s everywhere. Shorten the pause: the sim thread copies the dirty raw chunks into the save buffer (A16.4's line raised from 160 to 320 MB, paid from the areas line, finding 18), resumes the world, and compression and writing follow on the workers and the I/O thread; only dirty data beyond the buffer is compressed while paused. Budgets: pause ≤ 20 ms at `MIL-01`, ≤ 50 ms at `MIL-04`, ≤ 100 ms at the end of the arc; written per save ≤ 5, 30 and 120 MB; the write volume per hour at top speed is reported by the phone benchmark.
Part: P9

### 4. [major] A15.3, A15.4 An APK every alpha, and binaries kept out of `main`'s history
Problem: `PLT-06`, `PRC-11` and `SCP-03` (Decided): every alpha ends with a file installed on the phone. A15.4 builds the APK only when an alpha changes something Android-specific and at stage ends, the web page standing in; a page is not an install, and it lacks the writer, AAudio, heat guards and overnight mode. `dist/web/` (wasm up to 12 MB) is committed every alpha and merges are never squashed, so every wasm and APK stays in `main`'s history for good; A17.10's way out (release assets) is unavailable (finding 1).
Fix: an APK every alpha (`tools/build-apk.sh release`, about 2 minutes); the web page stays an extra and the screenshot target. `dist/web/` is gitignored: the published page holds it and any commit rebuilds it. `dist/kindling.apk` ≤ 20 MB (symbols kept outside, recordings within A13's 4 MB, no ONNX: finding 9), committed once per alpha; each stage report gives the repository's size (about 70 alphas × ≤ 20 MB ≈ 1.4 GB over the arc). With the token of finding 1, each alpha's APK goes to a release instead and nothing binary enters git.
Part: P9

### 5. [major] A15.5, A14.10 Signing: one key from the first alpha; harden the derivation
Problem: `PLT-06` and `RSK-29`: one key, set up before the first alpha, each alpha installing over the last and keeping every world. A15.5 starts on a committed debug key and switches by export, uninstall and import, which also drags export and import into `MIL-01` (A14.10). The derived key itself works (APK signature schemes v2 and v3 accept ECDSA P-256; `apksigner sign --key <pk8> --cert <der>` takes it; Python `cryptography` 49 is in the session image), but plain HKDF has no work factor while the certificate is public, so a weak passphrase can be guessed offline, and an environment variable is readable by every build script cargo, Gradle or npm runs.
Fix: the owner sets the passphrase before the first alpha, and a release build fails without it; no debug-signed APK is ever delivered: check builds sign with a key made in the session and discarded, and `android/keys/debug.jks` goes (A2.1 and A2.5 follow). Derivation: scrypt (n = 2^17, r = 8, p = 1, salt `kindling-release-v1`) to 48 bytes, reduced to a P-256 scalar; cargo, Gradle and npm run under `env -u KINDLING_SIGNING_PASSPHRASE`, so only `tools/signing-key.py` reads it. Before registering, confirm the developer console accepts an EC certificate (fallback: the base64 RSA keystore). If a key ever must change, rotate it with APK Signature Scheme v3 (`apksigner rotate`, then `--lineage`; Android 9 and later), which updates in place with no reinstall; export and import then take `PLT-08`'s own stage.
Part: P9

### 6. [major] A14.12 (against A2.2, A2.3, A2.6, A5.4) No `Storage` trait: `kd-save` does file I/O itself
Problem: A2.2 gives `kd-save` a `Storage` trait (`Platform::storage`, the web's IndexedDB; A2.3 rule 4: "files through `Storage`"), but A14.12 defines none: every call takes `root: &Path`, and an I/O thread inside `kd-save` does all file work. That breaks rule 4 (no `std::fs` or `std::thread` from `kd-core` to `kd-save`), cannot run on `wasm32-unknown-unknown`, which has no file system, and gives `kd-sim`, below `kd-save`, no way to fetch the dormant blocks A5.4 reads ahead and waits for mid-step.
Fix: in `kd-core::persist`: `trait Storage { read(path) -> Result<Vec<u8>>; write_atomic(path, bytes) /* temp, fsync, rename, folder fsync */; append_flush(path, bytes); list(dir); remove(path); free_bytes() -> u64 }` and `trait BlockReader { fn request(&self, k: ChunkKey); fn take(&self, k: ChunkKey) -> Option<Result<Vec<u8>, LoadError>>; }`, the latter passed to `advance_to`. `kd-save` takes `&dyn Storage` instead of `&Path`; `kd-app` implements both: native (`std::fs` and the I/O thread) and web (the in-memory map, flushed through `take_writes` transactions, manifest last).
Part: P9

### 7. [major] A3.1, A3.2, A3.5, A3.8 Determinism holes: signed zeros, `usize`, untested bans, web panics
Problem: (1) A3.2 allows `min` and `max`, but for −0.0 against +0.0 Rust's `f32::min`/`max` may return either input (x86 `minss` returns its second operand, ARM `fminnm` gives −0.0), and A3.5's `total_cmp` orders −0.0 before +0.0, so stored bits, state hashes and sort orders can differ between targets. (2) Nothing bans `usize` or `isize` in `bytemuck::Pod` columns or saved structs (A14.3); they are 4 bytes on wasm32 and 8 elsewhere, so layouts and hashes split and a web save can't open on the phone. (3) The clippy bans are "tested by the clippy bans": a mistyped path in `clippy.toml` silently bans nothing. (4) A3.8 and A2.6 catch panics in web exports, but on `wasm32-unknown-unknown` a panic aborts the instance.
Fix: `num::min`/`max` as `if a < b { a } else { b }` (and `>`), with `f32::min`, `max`, `minimum`, `maximum` added to `disallowed-methods`; stores write −0.0 as +0.0, beside the NaN rule. Saved and hashed types use fixed-width integers only, enforced by a `#[derive(Persist)]` that rejects `usize`/`isize` fields and asserts each type's size, plus a test that saves a world on wasm32 and opens it on x86. A fixture crate `tests/banned/`, using each banned type and method once, must fail clippy in `tools/check.sh`. Web: the panic hook shows the error line and offers to reopen the last save.
Part: P1

### 8. [major] A4.8, A4.10 (using A2.4, A2.6) On the web, acts and pauses land with clusters at different seconds
Problem: A2.4 lets a web step stop at any event boundary; A4.10 then keeps "each cluster in its place", and `now()` is the least second all clusters reached. A4.8 applies an act at `now() + 1` on the ground that "every cluster is at T"; after a mid-step stop a cluster may already have handled seconds past T + 1, so the act lands in its past (breaking the forward-only rule) and the web result differs from the phone's. Saves and state hashes taken at such a pause also hold clusters at mixed seconds.
Fix: pause, save, snapshot and `apply_act` only after `advance_to` returns `Reached`; on the web a pause request first finishes the current step over the next frames, each within its frame budget. Test: on wasm, an act confirmed after a random mid-step stop gives the native state hash.
Part: P2

### 9. [major] A13.9, A13.13 (against A15.3, A2.2, A2.8) The neural voice breaks the APK budget
Problem: The murmur ships ONNX Runtime (~15 MB) and a voice of up to 45 MB, to make each world's phrase bank on the phone. With `libkindling.so` and ML Kit the APK reaches about 70–80 MB: over A15.3's 50 MB, near GitHub's 100 MB file limit, about 75 MB of history per committed alpha (finding 4), and a C++ runtime (`libc++_shared.so`) that A2.2's crate list, A2.8's toolchain and `verify-apk.sh`'s public-libraries check don't allow. The web gets no murmur at all.
Fix: make A13.9's own fallback the design: `tools/voices.py` renders in the cloud, per base voice, every syllable the language generator can draw from `data/sounds/voice.md` (a fixed inventory, about 2,500 syllables of ~0.25 s), as 4-bit ADPCM at 16 kHz (≤ 5 MB a voice, in `assets/`); Rust strings syllables into phrases on the phone and the web alike. ONNX on the phone only if the owner hears a clear difference at `MIL-03`, with A15.3's cap then raised by the owner.
Part: P8

(2) Speeds are read after at least 3 minutes of full load (`PLT-04`), not 2 (A16.1). A15.10: about 20 minutes.

### 11. [major] A14.8, A16.5 History thinning ignores `PLT-10`'s 50 years
Problem: `PLT-10` (Decided): the last 50 game years keep every event; A14.8 thins each year once it is 10 years old. `PLT-10`'s target is a world of 1,000 people after 1,000 game years in about 2 GB, history and kept areas together; A16.5's history row (≤ 1 GB per 1,000 game years at 2,000 people) cannot hold with a 50-year window.
Fix: thin when a year turns 50. At 10 events a person a game day, 13 bytes each and 60-day years: 7.8 MB a game year per 1,000 people; 50 full years 390 MB plus 950 thinned years at 1 in 20 (370 MB) ≈ 0.76 GB at 1,000 people, ≈ 1.5 GB at 2,000. A16.5 rows: history ≤ 0.8 GB per 1,000 game years at 1,000 people and ≤ 1.6 GB at 2,000; a `PLT-10` total row: present state, kept areas and history ≤ 2 GB at 1,000 people after 1,000 game years (for example 0.3 + 0.9 + 0.8).

### 12. [major] A15.1, A15.9, A15.12, A15.13, A16.7 (and A3.1) Merge checks can't fit `PRC-10`'s ~20 minutes
Problem: Each run compiles five times (x86 tests, x86 release `kd-tools`, wasm release, Android release, aarch64 Linux for qemu), and the release profile (`codegen-units = 1`, thin LTO) also builds `kd-tools`, so every scene edit relinks with LTO. A3.1 checks cross-target hashes on every short scene before each merge (A15.9 says one scene), qemu running several times slower. The reviewer then repeats the whole run on a fresh machine: about 6 minutes of setup and up to 30 minutes cold (A16.7). A merge costs about an hour of wall time, and A16.7 plans to move scenes to nightly when the checks pass 20 minutes, which `PRC-10` forbids for scenes up to 10 game years.
Fix: `[profile.fast]` (opt-level 3, codegen-units 16, incremental, no LTO) for `kd-tools`, scenes and tests: float results don't depend on the profile, so hashes equal release's; LTO and `codegen-units = 1` only for the delivered APK and wasm. Per merge: `PRC-10`'s repeat check (one scene and one benchmark world, 1 core against 4 with a stop and resume) plus one fixed short scene on x86, arm64 under qemu and wasm in headless Chromium, all on the fast profile; every quick scene cross-target nightly (A3.1 follows). The release APK and wasm only at an alpha's delivery or when `android/`, `web/`, `kd-android` or `kd-web` change (step 2's `cargo check` for both targets stays). The reviewer re-runs format, clippy, tests and quick scenes on the fast profile and reverts each new test. Over 20 minutes: make scenes cheaper or split them; never move scenes up to 10 game years out of the merge set.

### 16. [minor] A2.2, A2.3, A2.5 Three interfaces that don't compile or aren't sound
Problem: (1) `Pool::run<R>` is generic, so `Pool` can't be a trait object, yet A4.10 takes `pool: &dyn Pool`. (2) A2.2's sketch, A2.3 rule 3 and A4.14 have `kd-player`'s director and recognisers take `&World`, a `kd-sim` type above `kd-player`; A10 uses a `DirectorQuery` trait instead. (3) `App` mixes `&mut self` calls on the GL thread with `&self` calls "from any thread" through one JNI handle: a `&App` on the UI thread while the GL thread holds `&mut App` is undefined behaviour, and `back() -> bool` must answer synchronously from card state the GL thread owns.
Fix: (1) `fn run(&self, jobs: usize, job: &(dyn Fn(usize) + Sync));` plus a free `pool_map<R: Send>(pool: &dyn Pool, n: usize, f: impl Fn(usize) -> R + Sync) -> Vec<R>` writing into per-job slots. (2) The sketch and rule 3 say `&dyn DirectorQuery`, implemented by `kd-sim` over `&World`, which keeps rule 3's guarantee. (3) `App::new` returns `(App, AppHandle)`: `App` for the GL thread (`gl_ready`, `resize`, `frame`, `audio`) and `AppHandle: Send + Sync` for the UI thread (`input`, `pause`, `resume`, `back`, `device`, `reply`), built on queues and atomics; `back()` reads an atomic count of closable cards published each frame and queues the close.
Part: P1

### 17. [minor] A3.4 Area uids can be reused
Problem: Area-space uids carry a 7-bit epoch (its map stores a `u8`), raised whenever a kept area's record is deleted. A foraging area stripped every year loses its last mark at the next ripening (A5.4), so its record can come and go yearly, and the epoch wraps after 128 cycles, reusing uids that history and memories still hold, against "never reused". A3.4 also says area generation numbers contents by ordinal, while A5.3 gives seed contents place uids.
Fix: `01 · area (25) · epoch (12) · ordinal (25)`, with the epoch a `u16` in the map; at epoch 4,095 an emptied record is kept rather than deleted. Text: the area space serves only things made by area processes and catch-ups; seed contents are place uids (A5.3).
Part: P1
